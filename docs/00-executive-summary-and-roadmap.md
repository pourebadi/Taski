# سند ۰۰ — خلاصه مدیریتی و نقشه راه اجرایی

> مبنا: `PRD v3.4 — Local-first / Self-contained MVP`
> وضعیت: پیش‌نویس ۱ | تاریخ: مرداد ۱۴۰۵
> مخاطب: صاحب پروژه، مدیرعامل، تیم فنی

---

## ۱) محصول در یک پاراگراف

یک **سیستم‌عامل اجرای محصول و پروژه** برای یک تیم پنج‌نفره؛ نه یک تسک‌منیجر عمومی. تفاوت اصلی‌اش با ابزارهای موجود سه چیز است: هر کار همزمان دو محور مستقل دارد (مرحله اجرا در برابر سلامت تحویل)، هیچ کار جدیدی بدون عبور از Intake و مشخص شدن «چه چیزی عقب می‌رود» وارد اجرا نمی‌شود، و هر تعهد زمانی تاریخچه‌ی غیرقابل حذف با علت تغییر دارد. خروجی نهایی این است که جلسه‌ی هفتگی مدیریت فقط با داده‌ی داخل سیستم اداره شود، بدون اسپردشیت و روایت شفاهی.

## ۲) مسئله‌ای که حل می‌شود

| علامت فعلی | چیزی که سیستم عوض می‌کند |
|---|---|
| معلوم نیست الان واقعاً روی چه چیزی کار می‌شود | فهرست واحد کارهای در جریان با Owner و وضعیت |
| کار جدید بی‌سروصدا وارد می‌شود و کار قبلی عقب می‌افتد | Intake اجباری + ثبت کار جابه‌جاشده |
| تاریخ‌ها بدون فرض و ریسک اعلام می‌شوند و بی‌صدا جابه‌جا می‌شوند | ETA با Confidence و Assumption + تاریخچه‌ی تغییر با علت |
| تصمیم‌ها گرفته می‌شوند و بعداً کسی دلیلشان را یادش نیست | Decision Log |
| ظرفیت تیم صرف پشتیبانی و کار برنامه‌ریزی‌نشده می‌شود بدون آنکه دیده شود | Work Stream چهارگانه + سهم ظرفیت |

## ۳) تصمیم‌های قفل‌شده معماری (نسخه ۳.۴)

```
Browser → یک URL عمومی → یک Runtime واحد NestJS
                            ├── /api/v1/*  REST
                            ├── /*         React build
                            ├── SQLite     data/app.db
                            └── Files      data/uploads/
```

- **بدون** Postgres مدیریت‌شده، Redis، Queue، S3، SMTP، OAuth/SSO، Kubernetes یا دو دیپلوی جدا.
- گیت‌هاب فقط منبع کد است؛ `data/` هرگز commit نمی‌شود.
- تنها الزام میزبانی: دیسک پایدار که بعد از Restart باقی بماند.
- تک‌اینستنس اجباری است (SQLite اجازه‌ی Scale افقی نمی‌دهد).
- خروج بدون هزینه: اگر پایلوت رد شد، حذف Runtime و Repo کافی است.

## ۴) دامنه‌ی MVP

**داخل دامنه:** احراز هویت و ساخت کاربر توسط ادمین، RBAC، تیم، پروژه، Work Item با سلسله‌مراتب، Board/List، My Work، Intake و Triage، ETA و تاریخچه‌اش، Blocker و Dependency، Decision Log، Weekly Review پایه، داشبورد مدیریتی پایه، Audit بحرانی، فارسی‌سازی کامل با تقویم شمسی و RTL.

**خارج از دامنه‌ی MVP:** SSO، اپ موبایل، تایم‌ترکینگ کامل، Custom Field، Workflow قابل تنظیم، اتوماسیون‌ها، یکپارچگی با ابزارهای بیرونی، AI، Forecasting، Portfolio Management.

## ۵) نقشه راه — هفت فاز

برآوردها برای **یک توسعه‌دهنده‌ی تمام‌وقت با کمک AI** است. با تیم دونفره حدود ۴۰٪ کوتاه‌تر می‌شود.

| فاز | عنوان | مدت تخمینی | خروجی قابل نمایش |
|---|---|---|---|
| ۰ | تثبیت Scope و اسکلت UX | ۳–۵ روز | Data model v1، ماتریس دسترسی، Wireframe، ADRها |
| ۱ | Foundation | ۱.۵–۲ هفته | ورود کاربر، ساخت کاربر توسط ادمین، تیم، RBAC، پوسته‌ی فارسی RTL |
| ۲ | هسته‌ی پروژه و Work Item | ۲–۳ هفته | پروژه، تسک، Board، My Work، کامنت، Activity |
| ۳ | Intake + اولویت + ETA | ۱.۵–۲ هفته | صف ورودی، Triage، ETA با تاریخچه و علت |
| ۴ | ریسک، پشتیبانی، تصمیم | ۱–۱.۵ هفته | Blocker، Dependency، Decision Log، دسته‌بندی Support |
| ۵ | ظرفیت، مرور هفتگی، گزارش | ۱.۵–۲ هفته | Agenda خودکار جلسه، گزارش هفتگی و ماهانه |
| ۶ | Hardening | ۱ هفته | Backup/Restore، تست رگرسیون، بازبینی امنیت، دسترس‌پذیری |
| ۷ | پایلوت و Rollout | ۴ هفته (موازی با استفاده) | ورود کار واقعی، آموزش، رفع اصطکاک |

**مجموع تا پایلوت قابل استفاده: حدود ۹ تا ۱۲ هفته.**

### مسیر بحرانی

```
Auth/RBAC → Work Item Core → Board/My Work → ETA History → Weekly Review
```

هر چیزی خارج از این زنجیره قابل تعویق است. اگر زمان کم آمد، Gantt، گزارش ماهانه، Handoff و Feature Brief اولین چیزهایی هستند که به بعد از پایلوت منتقل می‌شوند.

### نقطه‌ی «اولین ارزش واقعی»

پایان فاز ۲ به‌علاوه‌ی تاریخچه‌ی ETA از فاز ۳. یعنی حدود **هفته‌ی ۵ تا ۶**، تیم می‌تواند کار واقعی را از ابزار قبلی منتقل کند و از همان روز از سیستم استفاده کند. تا آن لحظه هیچ ارزشی به کاربر نهایی نمی‌رسد — این مهم‌ترین ریسک زمان‌بندی است.

## ۶) برنامه‌ی ۳۰ روزه‌ی سازمانی (بعد از آماده شدن MVP)

| هفته | هدف | Gate |
|---|---|---|
| ۱ — نقشه‌ی واقعیت | ثبت همه‌ی کارهای باز، Owner، Stream، سلامت | ۹۰٪ کارهای مهم دسته‌بندی و Owner شده |
| ۲ — بازتنظیم اولویت | انتخاب ۳ تا ۵ خروجی واقعی ۳۰ روزه | فهرست اولویت و فهرست به‌تعویق‌افتاده ثبت شده |
| ۳ — قانون تعهد | هیچ تاریخی بدون Scope، ریسک و فرض اعلام نشود | ETA همه‌ی P0/P1 با Confidence ثبت شده |
| ۴ — گزارش مدیریت | اولین گزارش واقعی و جلسه‌ی تصمیم | گزارش ماهانه از داده‌ی سیستم تولید شده |

## ۷) معیار موفقیت پایلوت

پایلوت موفق است اگر بعد از ۳۰ روز:

1. بیش از ۹۰٪ کار در جریان تیم داخل سیستم ثبت شده باشد.
2. جلسه‌ی هفتگی بدون اسپردشیت جانبی برگزار شود.
3. هر تغییر ETA علت ثبت‌شده داشته باشد.
4. مدیرعامل بتواند بدون پرسیدن از افراد به پنج سؤال کلیدی پاسخ بدهد.
5. تیم پنج‌نفره داوطلبانه به ابزار قبلی برنگردد.

معیار شکست هم باید صریح باشد: اگر تیم برای اطلاع از وضعیت همچنان مجبور به پرسیدن شفاهی باشد، ابزار مسئله را حل نکرده و باید ساده‌تر شود، نه بزرگ‌تر.

## ۸) پنج ریسک اصلی و پاسخشان

| ریسک | پاسخ |
|---|---|
| ابزار سنگین‌تر از نیاز ساخته شود | قفل Scope؛ هر افزوده باید یکی از ۱۰ سؤال مدیریتی را پاسخ بدهد |
| کاربران وضعیت‌ها را به‌روز نکنند | حداقل فیلد اجباری، ورود سریع، به‌روزرسانی گروهی، پرچم کار راکد |
| متریک‌های فردی به ابزار ارزیابی عملکرد تبدیل شود | در سطح مجوز مسدود شود، نه فقط در سیاست نوشتاری |
| دیسک Runtime پاک شود و داده برود | بکاپ روزانه‌ی خودکار + تست بازیابی واقعی قبل از پایلوت |
| گلوگاه Review در تیم کوچک | قانون استثنای ثبت‌شده وقتی Reviewer هم‌تخصص وجود ندارد |

## ۹) تصمیم‌هایی که همین حالا صاحب پروژه باید بگیرد

1. میزبانی پایلوت روی چه ماشینی انجام می‌شود و دیسک پایدارش چقدر است؟
2. آدرس و رمز ادمین اولیه (`ADMIN_EMAIL` / `ADMIN_PASSWORD`) چه باشد؟
3. آیا نفر دوم به‌عنوان ادمین پشتیبان تعریف می‌شود؟ (به‌شدت توصیه می‌شود)
4. آیا Gantt در پایلوت لازم است یا به بعد موکول می‌شود؟
5. شروع هفته‌ی کاری و روزهای تعطیل رسمی برای محاسبه‌ی روز کاری چیست؟
